# 運用中のブラウンアウトリセット — 調査の結論（Issue #74）

LTE-M 版（`xiao-s3-aws-lte-relay-pot`、`xiao-e83dc1fb05fc`）で起きたブラウンアウトリセットの調査の**結論だけ**をまとめる。調査の経緯・生データ・途中の誤った見立てとその訂正は、[Issue #74](https://github.com/makeOurCity/parking-status-sensor/issues/74) のコメントを参照。

- 対応する Issue: #74（調査）、#76（切断処理の修正）
- 関連: [hardware.md](hardware.md)（給電経路・電池の持ち）、[power-measurement.md](power-measurement.md)（計測手順）

## 1. 現象

| 項目 | 内容 |
|---|---|
| 発生 | 2026-09-25 14:58、09-26 17:55、09-26 22:21（JST）の 3 回。全期間（2026-07-06〜）でブラウンアウトはこの 3 回だけ |
| 記録 | テレメトリの `power.resetReason=brownout`（bootCount が 1 に戻る） |
| 起きたとき | 3 回とも定期送信（heartbeat）の起床で、LTE-M を使い始めたあと |
| 復帰 | 3 回とも、直後の再起動で 1 回目の送信に成功した。送信の欠損（75 分を超える空白）はない |
| 電池 | 電池 #1。Deep Sleep 中で約 3.70V、LTE の送信時は最低約 3.27V まで落ちていた |

### 1.1 記録は本物である

`resetReason=brownout` は、**ESP32-S3 自身の電源電圧が、ブラウンアウト検出のしきい値を下回ったことをハードウェアが検知した場合にだけ**記録される。ESP-IDF v4.4.7（Arduino-ESP32 2.0.17）のソース、ファーム、IoT Core のルール、Lambda（デプロイ済みのコードを取得して確認）を全段階で確認した。

- `ESP_RST_BROWNOUT` になる経路は、起動理由レジスタが `SYS_BROWN_OUT` の場合と、ブラウンアウト検出の割り込み処理 `rtc_brownout_isr_handler()` が書いた目印が残っている場合の 2 つだけ。目印を書くのはこの割り込み処理だけで、目印は毎回の起動時に消される
- しきい値は `CONFIG_ESP32S3_BROWNOUT_DET_LVL=7`（最も低いレベル）
- どこで電圧が落ちたか（電池か、3V3 レールか）は記録からは分からない。電圧が一気に大きく落ちた場合は `power_on` として記録される可能性がある（見逃しはありうる）

## 2. 原因（一番有力な説明）

**電池の電圧が下がった状態で LTE-M が送信すると、Grove Shield の 3.3V 降圧コンバーター（ETA3410）が 3.3V を保てなくなり、同じ 3.3V ラインから給電されている ESP32-S3 の電源電圧が落ちてブラウンアウトする。**

### 2.1 給電経路（回路図で確認した事実）

電池で動かしているとき、5V 系統は無効で、**ESP32-S3 と LTE-M（U128 → SIM7080G）は ETA3410 の 3.3V 出力を共有している**。詳細は [hardware.md](hardware.md) の「LiPo 単体運用時の給電経路」。

```
LiPo → SW1 → ETA6003（BATT → SYS）＝ VSYS
  → ETA3410（降圧、≈3.33V）＝ Shield の「3V3」
      ├ XIAO の 3V3 ピン → ESP32-S3
      └ Grove UART の VCC → リレー（#46）→ U128「+5V」→ SY8003A（≈3.32V）→ SIM7080G
```

### 2.2 電圧の条件

| | 電池 #1（ブラウンアウトあり） | 電池 #2（ブラウンアウトなし） |
|---|---|---|
| Deep Sleep 中の電圧 | 約 3.70V | 約 4.08〜4.10V |
| LTE の送信時の最低電圧 | 約 3.27V | 3.73V |
| 期間 | 09-24〜26 | 09-27 14:58〜09-29（約 44h） |
| ブラウンアウト | 3 回（満充電と思っていた時点から 36.6h 後に初回） | 0 回 |

- 電圧は U200 高速ロガーの値（電池の端子電圧＝デバイスが受け取る電圧）。テスターの値と一致することを確認済み
- ETA3410 は、入力（VSYS）が 3.3V より十分高いうちは LTE の大電流があっても 3.3V を保てるが、入力が 3.3〜3.4V 付近まで下がると保てなくなる（出力が入力電圧まで上がりきる動作）。電池 #1 の送信時の最低 3.27V は、ちょうどこの範囲にあたる
- 電池 #1 は傷んでいたのではなく、**満充電になっていなかった**だけと考えられる（充電すると 4.1V 程度に戻った）

### 2.3 否定・除外したこと

- 記録の誤り、人の操作、電池 #1 の個体の異常（容量低下・保護回路の損傷）
- 8/25 の現地試験の停止（極性逆接続による IC の焼損。別件）
- リレー ON の瞬間の突入電流が主犯であること（落ち込みは約 80〜110mV で、LTE の送信バースト時の約 370〜440mV より小さい。ただし 0.46ms より短い現象は見えていない）

### 2.4 未確認のこと

- **同じファームのまま電池を 3.7V 前後まで下げて、ブラウンアウトが再現するか**は試していない。電池 #1 と #2 ではファームも違う（#76 の修正前と後）。修正で変わったのは送信後の約 75mA の区間だけで、ブラウンアウトに関係する大電流の区間は変わっていないので、影響は小さいと考えている
- ブラウンアウトが**決まった残量で起き始めるのか**
- Shield の SW1 の「Imax=500mA」の注記の意味（LTE の送信時は 600mA 超が流れる）

## 3. 対策と方針

| 対策 | 判断 | 理由 |
|---|---|---|
| LTE-M だけ給電経路を変える（電池の + から直接給電する） | **採用しない** | 本機の設計思想（汎用性と容易さの両立）に反し、LoRaWAN 版（#40）との統一性も崩れる。LTE-M 版は LoRaWAN で通信できない場合だけ使う想定で、本流ではない |
| 切断処理の約 30s の空待ちをなくす（#76） | **実施済み**（PR #80） | 送信 1 回で約 51s・1.3 mAh → 16.8s・0.44 mAh |
| **ブラウンアウトを「すぐ充電」の合図にする** | **採用** | 原因が電池の電圧低下でほぼ説明できるため。下記 3.1 |
| ブラウンアウトが続いたら、間を空けてから再試行する | **実装しない** | ループ中は間を空けても送れない。2 回続く時点で電圧低下は深刻で、処理を複雑にする価値がない。再現試験も難しい。連続ループに入った場合は LiPo 自体の保護回路に任せる |
| 電池電圧をテレメトリに入れる | 当面見送り | Grove Shield に空きポートがなく、はんだ付けが必要 |

### 3.1 「ブラウンアウト = すぐ充電」の運用

- **1 回目のブラウンアウトが「すぐ充電」の合図**。1 回目は、今の作りのまま直後の再起動で送信できる見込みが高い
- 合図が出てから止まるまでの猶予は短いと考える（電池 #1 では、1 回目 → 27h 後に 2 回目 → その 4.4h 後に 3 回目と間隔が縮んだ）。猶予は 1〜2 日程度が目安（1 例からの推測）
- 充電が間に合わずに連続ループに入ると、電池の保護回路が働くまで LTE-M への通電を繰り返す。そうならないよう、合図が出たら早めに充電する
- 見落とさないよう、log-viewer の状態変化の通知（#70）に「ブラウンアウトが起きた → 充電してください」を加える（**未着手**）
- **LoRaWAN 版では、この合図は出ない可能性が高い**。LoRaWAN は送信時の電流が小さく、同じ仕組みでブラウンアウトが起きにくいため。LoRaWAN 版の充電の目安は別に考える

### 3.2 ブラウンアウトの実害

1 回だけなら実害はほぼない（ファームで確認済み）。

- sync ledger（`pss_sync`）と履歴ログ（#47）は NVS にあるので消えない。再起動後は判定し直し、センサーを読み直した値ですぐに送信する。送ろうとしていた送信内容そのものは消えるが、最新の読み取り値が約 20s 遅れで届く
- 起動時に必ず一度リレーを OFF にするので、LTE-M が通電しっぱなしにはならない。ブートモード（#50）は `ESP_RST_POWERON` のときだけなので、ブラウンアウトでは動かない
- 消えるのは RTC メモリにあるもの（bootCount、consecutiveTimerWakes、LTE のキャッシュ）だけ。キャッシュが消えるので、直後の送信だけネットワーク接続に約 16s かかる（通常は約 7.5s）

## 4. 電池の持ち（実測ベース）

電池 #2・#76 修正後のファームで、約 44.5h の U200 高速ロガーの記録から求めた値。数値の詳細と試算は [hardware.md](hardware.md) の「稼働日数の試算」を参照。

| 項目 | 実測 |
|---|---|
| Deep Sleep 中の電流 | 0.43 mA（平均） |
| LTE を使わない起床 1 回（4.8s） | 0.0475 mAh |
| LTE で送信する起床 1 回（16.8s） | 0.446 mAh |
| ブートモード 1 回（約 4 分、送信 5 回） | 4.67 mAh |

状態変化がなければ約 122 日、毎回送信なら約 29 日（使える容量 3,960 mAh として）。ただし LTE-M 版は、電池の電圧が下がるとブラウンアウトが起き始めるので、実際に使えるのはその手前まで。一般的な LiPo の目安では、休ませたときの 3.7V は残量 10〜15% 程度だが、電池の種類・個体で変わり、未確認。

## 5. 計測で得た注意点

- **U200 高速ロガー**（`logger-devkit-fast`、#75）で、電圧を約 0.46ms 間隔で記録できる。通常モードの `setAverage(4)` は実際には 128 回平均（約 282ms）で、ms 単位の落ち込みは見えない。使い方は [tools/power-logger/README.md](../tools/power-logger/README.md)
- **バッテリーチェッカー（Capacity Controller）**で 1S の LiPo を測るときは、**NiCd/NiMH 側の差し込み口**に差す。Li-ion 2S〜7S 側に差すと正しく測れない（電池 #1 で 0.33V 高く表示された）。電圧の基準はテスターにする
- **電池には個体番号を付けて記録する**（#1、#2 …）。番号がないと、どの電池で何が起きたか追えない
- CloudWatch Logs の `aws logs filter-log-events` を長い期間で 1 回呼ぶと取りこぼしが出たことがある。日単位など短い期間に分けて取得する
- `tools/power-logger/integrate_mah.py` は、記録ファイルに見出し行（`ms,samples,...`）がないと、高速モードのログのサンプル数の列を電流として足してしまう（**未修正**）。`pio device monitor` をロガーの起動後に始めると見出し行が入らないので、そのときは `current_avg_mA`（7 列目）を直接集計する

- 計測の途中結果（起床ごとの電圧・電流の表、XIAO のシリアルログ）は [tools/power-logger/results/74/](../tools/power-logger/results/74/README.md)。生の CSV は失われた（git の管理外だったため）。今後の生の CSV はリポジトリの外に保存する
