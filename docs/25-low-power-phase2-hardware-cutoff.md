## 1. 発端：現地試験での早期電池切れ

> **原因確定（2026-09-26 追記）:** この停止は電池切れでも消費電力の問題でもなかった。**LiPo を極性逆に接続したことで電流制御 IC が焼損していた**ハードウェア故障である。以下 §1.1〜§1.3 は原因確定前の分析記録として残すが、§1.2 の「16倍のギャップ」、§1.3 の保護回路トリップ仮説はいずれも**当てはまらない**。消費電力の見積もり（[hardware.md](hardware.md)）の妥当性を疑う根拠にも使わないこと。

2026-08-25 の現地試験で、バッテリーが**10時間ちょっとで切れた**という報告があった。Phase 0 実測（待機 ≈22mA）に基づく試算では同条件で **約7日** 持つはずであり、大きな乖離がある。

### 1.1 CloudWatch ログ分析（`/aws/lambda/parking-status-bridge`）

対象日 10:00〜21:00 JST の受信テレメトリを解析した結果:

| 項目 | 内容 |
|---|---|
| 準備段階 | 10:20〜10:35 の間に `power_on` リセットが計7回発生（現地での電源入れ直し跡と推定） |
| **安定稼働区間** | **10:40:16（boot=2）〜21:00:11（boot=109）** |
| 継続時間 | **10時間19分55秒**、108サイクル |
| サイクル周期 | 約346秒（300秒スリープ + 平均7.4秒アクティブ） |
| 通信品質 | 全サイクルで `transportAttempts=1` `publishAttempts=1`。接続タイミングも #30 改善どおり正常範囲 |
| 停止のしかた | **21:00:11 を最後に、劣化の予兆なく突然メッセージが途絶えた** |

ユーザー報告の「10時間ちょっとで電池切れ」と、この安定稼働区間の長さはほぼ一致する。

### 1.2 Phase 0 試算との矛盾

Phase 0 実測のスリープ電流 ≈22mA がそのまま現地でも成立していたと仮定すると:

```
22 mA × 10.33h ≈ 227 mAh
```

これは LiPo 4,400mAh（実効 3,960mAh）のわずか 5〜6% にしかならない。同じ前提なら本来 ≈7日（168時間）持つはずが、実際は10時間強で停止しており、**16倍のギャップ**がある。

一方でテレメトリには通信の劣化・リトライ増加・テストファーム的挙動（Deep Sleep 未使用の連続動作等）の痕跡が一切ない。ソフトウェア側は最後まで正常に動作していたと考えられる。

### 1.3 有力な仮説：バッテリー保護回路の電圧トリップ

「総消費量はわずかなのに、予兆なく突然停止する」という挙動は、**バッテリー残容量が尽きたのではなく、劣化・内部抵抗増大したセルがLTE送信バーストのピーク電流（README想定で100〜250mA）で瞬間的に電圧降下(sag)を起こし、保護回路の低電圧カットオフが作動した**、というパターンに典型的に一致する。保護ICは残容量ではなく電圧を監視するため、実容量が残っていても瞬間的に電圧が閾値を割れば即座に完全遮断される。

このバッテリーが Phase 0 のベンチ試験で繰り返し抜き差し・放電されたものであれば、内部抵抗が上がり現地でこの現象が起きやすくなっていた可能性がある。

**未解決の論点:** この仮説は状況証拠からの推定であり、確定はしていない。電圧の時系列データが現地では取得できていないため（§4 参照）。

**→ 解決済み（2026-09-26）:** 原因は極性逆接続による電流制御 IC の焼損と確定し、この仮説は棄却された（§1 冒頭の注記参照）。

## 2. ハードウェア設計：LTE-Mモジュールの電源遮断（旧方式：ラッチングリレー・廃止）

> **廃止（2026-10-07）:** 以下 §2.2〜§2.7 は、2026-09 に採用した**旧方式**の設計記録。リレーのコイルは 5V 定格なのに、このプロジェクトでは 3.3V で駆動しており、これは設計時の仕様確認の誤りだった（§2.8）。LTE-M の電源遮断は、ロードスイッチ基板に置き換える（[88-load-switch-design.md](88-load-switch-design.md)、[hardware/lte-power-switch/](../hardware/lte-power-switch/)、#88）。新しく作る機体には使わない。§2.1 の根本原因は、方式に関係なく今も有効。

### 2.1 根本原因（Phase 0 で確定済みの制約）

Grove Shield のポートVCCは3.3Vレール直結・分岐なし・GPIOによる電源スイッチなしという回路仕様のため、`esp_deep_sleep_start()` はESP32本体のみを止め、LTE-Mモジュールへの給電は切れない（[25-low-power-mode.md](25-low-power-mode.md) §1.2, §1.4）。`modem.poweroff()` を送っても NETLIGHT は消灯せず、Grove構成でのソフトウェアのみによる電源断は不成立というのがPhase 0の結論だった。

今回の早期電池切れの原因究明とは独立に、**この待機電流を物理的に断つ対策**を実施する。

### 2.2 採用していた方式（廃止）：Grove 2-Coil Latching Relay

| 項目 | 内容 |
|---|---|
| 製品 | Grove - 2-Coil Latching Relay（Seeed SKU 103020010） |
| 仕様 | 切替電流最大3A、切替電圧最大35VAC/35VDC。コイルは **5V 定格**（動作電圧 4.7〜5.3V、Set/Reset 電圧は最大 4.0V、コイル抵抗 167Ω）。Set/Reset 時間（各 4.5ms／3.5ms 以下）は定格電圧のときの値（下の訂正を参照） |
| 特長 | **状態を保持する間は電力を必要としない**（パルスでのみ切替）。ON/OFFいずれの状態でも保持電流ゼロ |
| 調達 | 共立エレショップ（[gK5F121](https://eleshop.jp/shop/g/gK5F121/)）に自社在庫あり、¥1,650、**発注済み** |

**このリレーは 5V 品で、3.3V での動作保証はない。** Seeed Wiki とデータシート（Hongfa HFD2/005-S-L2、4 ページ版）によると、動作電圧は 4.7〜5.3V、Set/Reset 電圧は最大 4.0V。3.3V での動作保証は Wiki にもデータシートにも見つからない（データシートの注に「3V 駆動なら 2.4V 品を推奨」とある）。初版（2026-09-16）の「制御電圧 3.3V/5V」は、この Wiki の記載と食い違っていた（#90 で訂正）。

一方、このプロジェクトでは Grove ポートの VCC が Shield の 3V3 レール（約 3.33V、§2.4 と [hardware.md](hardware.md) 参照）なので、**リレーは定格を下回る電圧で駆動されていた**。回路図（Eagle v1、2013 年）から見積もると、SET コイルは D8（1N4148）の降下ぶん不利で約 2.6V（Set 電圧の最大値 4.0V の約 64%）、RESET コイルは約 3.3V（約 82%）。この見積りはシミュレーションで、**実測ではない**（現物が同じ回路かも未確認）。

基板上の **LED が光ることは、コイルに十分な電流が流れた証拠にならない**（LED はコイルと別の経路で、約 0.5mA で光る）。

### 2.3 制御対象：LTE-Mモジュールのみ、センサーは常時通電のまま

| 対象 | 方針 | 理由 |
|---|---|---|
| **LTE-Mモジュール** | リレー経由でON/OFF | 待機 +21〜28mA の支配的要因（Phase 0確定） |
| **カラーセンサー** | **常時通電のまま**（リレーを介さない） | 待機寄与 +0.15mA と無視できる範囲。常時通電にすることで電源投入直後のI2C整定待ちも不要になり、むしろactive時間の短縮に寄与する |

リレーは2回路搭載だが、**1chのみ使用**（LTE-M用）。もう1chは未使用・将来の予備。

### 2.4 物理配線

リレー基板には **Grove 4pinコネクタ（制御用）** と **6pinネジ端子台（切替接点、Comm/NO/NC ×2回路）** という、独立した2つのインターフェースがある（製品写真で確認済み）。

- **制御側**：リレーのGrove 4pinコネクタを、ふつうのGroveケーブルでESP32側のGPIOポートに接続するだけ（加工不要）
- **切替側（要加工）**：LTE-Mモジュールへ向かうGroveケーブル4本（GND・VCC・UART TX・RX）のうち、**VCC の1本だけをケーブル途中で切って**リレーの6pinネジ端子台に通す
  - Shield側のVCC線 → ネジ端子「1COM」
  - LTEモジュール側のVCC線 → ネジ端子「1NO」
  - リレーが「Set」状態のときだけ Comm-NO が導通し、LTEモジュールに給電される
  - この VCC 線は、実際には **Shield の 3.3V（ETA3410 の出力）**。Grove Shield for XIAO の Grove ポートの VCC はすべて 3V3 につながっていて、電池で動かしているときは 5V 系統に電気が来ない（[hardware.md](hardware.md) の「LiPo 単体運用時の給電経路」、#74）。U128 側の入力名が「+5V」なので、ケーブル上は 5V 線と呼ばれていた
  - GND・TX・RXの3本はそのまま直結（リレーを経由しない）

### 2.5 ファーム側の動作フロー（実装予定）

現行の `mustPublish()` 骨格（[main.cpp:190](../firmware/src/main.cpp#L190)）と組み合わせる想定:

1. 起床
2. カラーセンサー読み取り（常時通電のため即座に可能、電源投入待ちなし）
3. 前回確定状態（`SyncLedger.lastConfirmedStatus`）と比較
4. **変化なし** → リレーに触れずそのままスリープ（LTE-Mは一切通電されない）
5. **変化あり** → リレーへSETパルス送信 → LTE-M起動・接続・publish → リレーへRESETパルス送信 → スリープ

変化なしサイクルではLTE-Mの通電自体が発生しなくなるため、待機電流の削減とactive時間の削減が同時に効く。

### 2.6 フェイルセーフ上の注意点（要実装）

ラッチングリレーは**電源が落ちても直前の状態を保持し続ける**。このプロジェクトでは実際に `#41（ファームウェア: 現場実証中にLTE接続処理でハング・publish停止、ウォッチドッグ未実装）` というLTE接続ハングの不具合が過去に発生し、ウォッチドッグでの検知・リセットを実装済みという経緯がある。

もしSETパルス送信後、RESETパルスを送る前にウォッチドッグリセットが発生した場合、**リレーはONの状態のまま固定され、LTE-Mモジュールが通電しっぱなしになるリスク**がある。

**対策（実装必須）:** `setup()` の一番最初、他のどの処理よりも前に、**必ず一度RESETパルスを送ってからスリープ状態相当まで戻す**安全策をファームに入れる。これにより、ウォッチドッグリセット後もLTE-Mモジュールは確実にOFFから再開される。

### 2.7 検討したが採用しなかった代替案

| 案 | 不採用の理由 |
|---|---|
| Grove MOSFET（103020008, CJQ4435） | Seeed公式Wiki自身に「外部電源端子を使わない場合、Grove側から負荷に回り込み電流が流れ得る」という注記があり、真のゼロ待機を保証するには回路図レベルの追加検証が必要だったため |
| 通常のGrove Relay（807/103020005, Normally-Open） | フェイルセーフ性（未通電時に自動でOFFへ復帰）は優れるが、ON保持中に約100mAのコイル電流が常時発生し、1サイクルあたり ≈0.4mAh の追加コストになる（Phase 0実測の1サイクル ≈2.1mAhに対し約2割の上乗せ）。ラッチングリレー側のフェイルセーフ欠如は§2.6の起動時安全パルスで代替可能と判断し、コイル電流ゼロを優先 |

（2026-10-07 追記）上の 2 案はいずれも、のちに #88 で採用した**ロードスイッチ IC** とは別物。ロードスイッチは MOSFET モジュールと違い、1〜5.5V で動く専用 IC で、OFF 時の電流が 0.5µA typ と小さく、ON ピンのプルダウンでステートレスに OFF へ戻る（§2.6 のフェイルセーフが構造的に不要になる）。

### 2.8 廃止の経緯と教訓（2026-10-07）

**経緯**

1. 2026-09-16: 本ドキュメント初版で、5V 定格のリレーを採用した。初版は、Grove ポートの VCC を 5V 系と想定していた（§2.4 の旧記述が「5V 線」）。また「制御電圧 3.3V/5V」と書いたが、Seeed Wiki の記載（動作電圧 4.7〜5.3V）と食い違っていた。
2. 2026-09-27（#74）: 電池運用では Grove ポートの VCC が、5V ではなく Shield の 3.3V（ETA3410）だと判明した。このとき追記したのは §2.4 の配線の訂正だけで、§2.2 のリレーの定格は見直されなかった（見直しは 10-02 の #90）。
3. 2026-10-02（#87）: ラッチングリレーが約 9 時間、SET パルスを約 340 回送っても切り替わらず、Grove ケーブルを差し直したら復活した。
4. #88 の机上調査で、定格外の駆動（SET コイルは見積りで約 2.6V、Set 電圧の最大値 4.0V の約 64%）が見つかった。リレーの完全故障かどうかは確定しなかった。
5. 2026-10-07: 5V 定格のリレーを選んだこと自体を設計上の誤りと判断し、リレーを廃止して、ロードスイッチ基板に置き換える方針にした。#88 の切り分け実験（[88-relay-experiment-sheet.md](88-relay-experiment-sheet.md)）は、旧機体の不具合調査として残る。

**教訓**

- **部品の定格電圧は、実際に給電するレールの電圧で確認する。** 選定の時点で、Grove ポートの VCC を 5V と想定したまま、実測や回路図でレールの電圧を確かめていなかった。レールが 3.3V だと分かった時点（#74）で、すでに選んだ部品の定格を見直すべきだった。
- **一次資料の記載と食い違う記述は、そのままにしない。** 初版の「制御電圧 3.3V/5V」は、Seeed Wiki の記載（4.7〜5.3V）と食い違っていたが、そのまま設計に使われた。
- **「LED が光る」は動作の証拠にならない。** 基板の LED は、コイルとは別の経路にあった。
- **状態が MCU の外に残る部品（ラッチング）は、故障モードが増える。** 「切り替わらない」「ON のまま戻らない」を、起動時の安全パルス（§2.6）で補う必要があった。ステートレスな部品なら、その対策が要らない。

## 3. 今回（2026-09時点）の投入スコープ

### 3.1 当初計画とのギャップ

もともとは、現地での電池切れ原因（容量切れ vs 電圧sag）を確定するため、**現地に電流・電圧を時系列で記録する専用ロガー（2号機・仮設プロトタイプ）を同時投入する**計画だった。ロガーには以下が必要:

- microSDカードによるスタンドアロン記録（PCに繋がず動作）
- RTCによる絶対時刻付与（CloudWatch側テレメトリとの突合用）
- ロガー自身の独立電源（DUTのバッテリーに影響しない）

このうち **RTC・I2Cハブ・Lipo Rider Plus（ロガー用電源）はSwitch Scienceへ発注済み**だが、**今回の投入までに間に合わなかった**。

### 3.2 今回の対応

**ハード電源遮断（§2）のみを投入し、ロガーなしで進める。**

| 項目 | 状態 |
|---|---|
| ラッチングリレーによるLTE-M電源遮断 | 投入する |
| 現地の電圧・電流時系列ロギング | **見送り**（部品未到着） |
| 効果測定 | CloudWatch側のサイクル間隔・稼働時間からの間接推定のみ |

ロガーがない以上、今回もし早期停止が再発した場合、判明するのは「今回は何時間で止まったか」までで、原因が容量切れか電圧sagかの直接的な切り分けはできない。ただし、**LTE-Mの待機電流を物理的に断った状態でも早期停止が再発するかどうか自体は重要な診断材料になる**：もし今回も短時間で停止するなら、原因はLTE-M待機電流以外（バッテリー個体の劣化・別の漏れ電流等）である可能性が高まる。

（2026-09-26 追記）8/25 の早期停止は極性逆接続による IC 焼損と確定したため（§1 冒頭の注記）、「容量切れ vs 電圧sag」の切り分けという当初の動機は解消した。ロガーは電池持ちの実測手段としての価値のみ残る。

### 3.3 次回以降への持ち越し

| 項目 | 状態 |
|---|---|
| ロガー用SDモジュール・大容量LiPo・防水ケース | 未発注（Seeed/Switch Science非取扱品、別途調達要） |
| ロガーのファーム（SD書き込み・RTC同期・間欠サンプリング） | 未着手 |
| ロガー同梱の2号機投入 | 部品到着後に再検討 |
